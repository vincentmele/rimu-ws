# Soak tier 1: the common soak and the competitor field. Implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run one common soak, unchanged, against rimu-ws and 14 competitors configured for
production. Produce a report card that shows rimu-ws passing every check, and every check failing
somewhere among the competitors.

**Architecture:**

- **Harness:** `rimu-ws-soak` gains a `common` judging mode. Each scenario then grades a failure as
  MUST or SHOULD, judges limit-dependent checks by survival only, and marks "limit below the common
  size". The monitor learns to watch a Docker container through its cgroup.
- **Competitors:** each lives in `rimu-ws-soak/competitors/<name>/` with a production `CONFIG.md`,
  and is built into a Docker image.
- **Running and reporting:** a runner script soaks every image round-robin, and
  `rimu-ws-soak report` turns the JSONL into the report card.

**Tech Stack:** Rust 2024 (tokio, serde, clap), bash, Docker (HttpArena's run flags), HttpArena at
commit `fdb4aae` (local branch `add-rimu-ws`).

**Spec:** `docs/superpowers/specs/2026-11-05-soak-gate-design.md`. This plan covers tier 1 and the
report card. Tier 2, the rimu-ws gate, is a separate plan written after this one lands, because it
builds on the mode, records and report made here.

## Review Focus

1. **A container whose server forks worker processes.** Memory and descriptors must be the sum
   over every process in the cgroup, not the first pid. Test: Task 4,
   `cgroup_monitor_sums_every_process`.
2. **A container that exits mid-run** (crash, OOM, the `--memory` cap). The run must end with a
   `PidGone` violation and a summary, not hang or report zeros. Test: Task 4,
   `empty_cgroup_is_pid_gone`.
3. **A server whose descriptors the harness can't read** (a root-owned process). The monitor must
   error out loudly, not report 0 descriptors and pass the leak checks. Test: Task 4,
   `unreadable_fd_dir_is_an_error`.
4. **A competitor image that never starts listening** (bad build, needs root, wrong port). The
   runner must record "did not start" for that row and go on to the next competitor. Test: Task 6,
   step 4 (a deliberately broken image).
5. **An io_uring entry that silently falls back to epoll.** The run must be marked invalid (exit
   code 4, `invalid` in the summary), not failed or passed. Test: Task 4,
   `io_uring_expected_but_absent_is_invalid`.

#### What the common mode changes

`Mode::Strict` keeps today's behaviour, except the two rows marked "both". Copy this table into
`RULES.md` with an RFC 6455 section for each row, along with the "Rule changes" list from the spec.

| Scenario | Common mode |
|---|---|
| `invalid`, MUST cases (BadUtf8, ReservedOpcode, Rsv1NoExtension, Unmasked, FragmentedControl, ControlTooLong, StrayContinuation, DataInsideFragmented) | No TCP close within 2 s is a `Must` fail. A close frame with a code outside `expected_codes`, or EOF with no close frame, is a `Should` fail. |
| `invalid`, BadCloseCode and OneByteClose | Not failing the connection within 2 s is a `Should` fail. |
| `invalid`, Oversized | Send it, wait 1 s, reset, `Pass` (survival). |
| `huge_len` | Send the header, trickle for 1 s, reset, `Pass` (survival). |
| `garbage` | Send, wait 1 s, reset, `Pass` (survival). |
| `header_flood` | Send up to `HEADER_CAP` and reset, then `Pass`. A 101 to the unterminated request is still a `Must` fail. |
| `bad_upgrade`, must-refuse cases | A 101 is a `Must` fail. No answer within 1 s is a `Pass`. |
| `bad_upgrade`, may-refuse cases | A wrong `Sec-WebSocket-Accept`, or an upgrade without the echo, is a `Must` fail. No answer is a `Pass`. |
| `bad_upgrade`, Pipelined refused (both modes) | A `Should` fail. Strict mode still fails rimu-ws on it, because every kind must pass there. |
| `slowloris` | Trickle the whole request, then reset, `Pass`. A 101 before the request is complete is a `Must` fail. |
| `never_read`, `ping_no_read` | Send for `never_read_budget`; blocking, closing or neither are all `Pass` (the monitor judges memory). Then read for 500 ms: any frame other than a pong carrying a sent ping payload is a `Must` fail. |
| `ctrl_in_fragments` (both modes) | A pong arriving after the echo is a `Should` fail. RFC 6455 5.5.2 says "as soon as is practical". |
| `half_close` | Every echo and the close are still a `Must`. With no close frame sent, the server's EOF is not awaited, because the monitor's CLOSE_WAIT check judges it. |
| `echo`, `frag_drip`, `slow_reader`, `frag_flood`, `zero_flood`, `split_every_byte` | When the server's close code is 1009 before every expected message arrives, the outcome is `Mark { "limit below the common size" }`, not a fail. `frag_drip` never goes over the limit. |
| `idle_pre`, `idle_post`, `close_linger` | Not in the `common` profile. |

`profile("common")` is the `untimed` mix plus `garbage=4,header_flood=1,slowloris=5`.

**Interfaces:**

- Produces:

  - **Memory and descriptors:** `rss_kib`, `hwm_kib`, `fds` and `cpu_ticks` are sums over every pid

  - **Unreadable `/proc/<pid>/fd`:** permission denied is `MonitorError::Unreadable`. The cycle
    reports it as a violation `Unreadable` and ends the run; it is never a sample with 0
    descriptors.

     - `--expect-io-uring` when `IO_URING=1`;

  7. Exit with the harness's code.

### Task 9: The report card

**Files:**

- Create: `rimu-ws-soak/src/report.rs`, `rimu-ws-soak/tests/report.rs`, and the fixtures
  `rimu-ws-soak/tests/fixtures/report/{a,b,dead}.jsonl`
- Modify: `rimu-ws-soak/src/main.rs` (subcommand), `rimu-ws-soak/src/lib.rs`

**Interfaces:**

- Consumes: `Summary`, `Violation`, `ScenarioCounts` (Tasks 2 and 4).
- Produces:
  - `pub fn load(paths: &[PathBuf]) -> Result<Vec<Summary>, String>`, which reads the last
    `summary` line of each file.
  - `pub fn merge(summaries: Vec<Summary>) -> BTreeMap<String, Summary>`, keyed by label, which sums
    the counts across rounds and concatenates the violations.
  - `pub fn card(rows: &BTreeMap<String, Summary>, gated: &str) -> String`, the Markdown.
  - CLI: `rimu-ws-soak report --gated rimu-ws --out PATH FILES...`.
- The card:
  - **Rows:** one per label. `gated` comes first, the rest alphabetically.
  - **Columns:**
    - one per scenario in `profile("common")`, with the cell `✓`, `MUST n`, `SHOULD n`,
      `limit n` or `n/a` (it never ran), several joined with ` / `;
    - one per survival violation variant (`PidGone`, `RssCeiling`, `Rss`, `Fds`, `CloseWait`,
      `Leak`, `Trend`, `Latency`, `ProbeFailures`, `NoRecovery`, `Burst`, `Busy`, `Unreadable`),
      with the cell `✓` or its count;
    - a final `invalid` column.
  - **Below the table:**
    - one example replay id per failing cell;
    - a "Gate" line: `rimu-ws: PASS` only if its row is all `✓`, and no `invalid`;
    - a "Toughness" list: every column where no competitor failed. Each needs a written reason in
      the tier 1 report (Task 10), or a harder scenario.

- [ ] **Step 1: Write the failing tests:**
  - `merges_rounds_by_label`: the two fixture files with the same label sum `runs` and `should`.
  - `gated_row_first_and_pass_line`: fixture `a` (label rimu-ws, all pass) and fixture `b` (one
    `SHOULD`). The card starts its rows with `| rimu-ws |`, contains `rimu-ws: PASS`, and lists
    `invalid` under Toughness when `b` never failed it.
  - `dead_server_shows_in_survival`: the `dead` fixture has a `PidGone` violation. Its row shows `1`
    in `PidGone`.
  - `did_not_start_is_invalid`: a summary that has only `label` and `invalid: "did not start"`
    loads, and shows in the `invalid` column.
- [ ] **Step 2: Run them and see them fail.** Run `cargo test -q -p rimu-ws-soak --test report`.
  Expected: compile errors.
- [ ] **Step 3: Implement.** Write the fixtures as real run output, cut down to a few lines.
- [ ] **Step 4: Run the whole crate's tests.** Run `cargo test -q -p rimu-ws-soak`. Expected: all
  pass.
- [ ] **Step 5: Commit:** `git commit -m "rimu-ws-soak: report card across servers and rounds"`.

### Task 10: The tier 1 runs and the report

**Files:**

- Create:
  - `.scripts/tier1.sh`
  - `docs/soak-tier1-report-YYYY-MM-DD.md`
  - the run output under `/mnt/nvme1tb/claude-tmp/soak/tier1-<date>/`, which is not committed

**Interfaces:**

- `.scripts/tier1.sh [--rounds N] [NAMES...]`. The defaults are 2 rounds and every competitor
  directory.
- **Order:** in round `r`, the competitors in alphabetical order rotated by `r`. Every competitor in
  round `r` gets seed `1000 + r`.
- **Each competitor, each round, runs two jobs through `competitor.sh run`:**
  1. **Soak:**
     `--mode common --profile common --slots 300 --duration 180s --cycles 3 --warmup 10s --drain 10s --burst 500 --records failures --heartbeat 60s`.
  2. **Descriptor flood:** a fresh container with `--ulimit nofile=1024:1024` in place of the
     nofile flag, and
     `--mode common --profile baseline --slots 20 --duration 20s --cycles 1 --fd-flood 1500`.
     `competitor.sh` gets an `FD_NOFILE` variable for this.
  
  Write the output to `tier1-<date>/r<round>/<name>{,-fd}.jsonl`.
- **Run it detached** with `systemd-run --user --unit soak-tier1 ...`. A session background job is
  killed at 2 hours.
- **Then:** `rimu-ws-soak report --gated rimu-ws --out tier1-<date>/card.md tier1-<date>/r*/*.jsonl`.

- [ ] **Step 1: Write `tier1.sh`.** Dry-run it with `--rounds 1 rimu-ws tokio-tungstenite` and
  shorter args passed through `TIER1_ARGS`. Expected: two rows on the card.
- [ ] **Step 2: Launch the full run** and check on it with `journalctl --user -u soak-tier1`.
  - 15 servers, about 11 minutes each, 2 rounds: about 5.5 hours.
  - Never start another soak while it runs.
- [ ] **Step 3: Write the report.** It contains:
  - the card;
  - the gate line;
  - for each competitor, its notable failures with a replay id;
  - the Toughness section, with each never-failed column given a written reason (for example "a
    rimu-ws bug class fixed on 4 Nov") or listed as needing a harder scenario in tier 2;
  - the HttpArena commit, the rules version and the run dates.
