# rimu-ws HTTP/3 + QUIC Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An own QUIC v1 transport, HTTP/3 + QPACK and an HTTP/3 server framework in rimu-ws, zero-allocation after warm-up, that takes #1 on the local experimental HttpArena h3 composite (baseline-h3 + static-h3) against plod, fib and aegon, behind a production gate.

**Architecture:** Sans-I/O cores (`wtx/src/quic/`, `wtx/src/http3/`) fed datagrams and drained into a TX arena, on the wtx TLS 1.3 stack in a new QUIC mode with keyed ring AEAD objects; one endpoint per pinned io_uring worker with multishot recvmsg, one flush per dirty connection per turn, GSO trains, CID-steering CBPF and least-loaded placement; an `Http3ServerFramework` that reuses the h2 framework's router with inline poll-once handlers.

**Tech Stack:** Rust nightly-2026-10-12, io-uring 0.7.15, ring 0.17.14 (AES-GCM/ChaCha20 + QUIC header protection), the wtx TLS 1.3 stack, h2load-h3 (nghttp2 1.69 + ngtcp2 + nghttp3 + quictls) in Docker for measurement.

**Spec:** `docs/superpowers/specs/2026-11-08-http3-quic-design.md` (approved 8 Nov; user decisions in its §10). Background reports: `/mnt/nvme1tb/claude-tmp/h3win/reports/*.md` (cited as `<report>.md §n`).

- Features: `quic = ["tls", "foldhash", "hashbrown"]`, `http3 = ["http", "quic"]`, `http3-server-framework = ["http2-server-framework", "http3", "io-uring"]` (the router lives in the h2 framework).

Full lib gate (`TEST_ALL`): `cargo test -p rimu-ws --lib --features http1-server-framework,http2-server-framework,http3-server-framework,web-socket-server-framework,crypto-ring,io-uring`.
- Crypto: TLS 1.3 only; suites AES-128-GCM, AES-256-GCM, ChaCha20-Poly1305 in that server preference order; groups X25519, P-256, P-384. Server key parsed once (existing `DynSigningKey`); pooled handshake state zeroed with `misc::zero_volatile`.
- Zero heap allocations after warm-up per packet, request and connection; the only budget is ring's 9 allocations per RSA handshake signature (`Owner::Crypto`).
- Lib allocation tests count with the existing harness: `crate::tests::_count_allocations_in(&COUNTER)` on the thread under test, after a warm-up round, asserting the count of the next round.
- Never send ACK_FREQUENCY, IMMEDIATE_ACK, PRIORITY_UPDATE, GREASE frames or settings, PING or PADDING except where the RFC requires them (anti-amplification padding, PMTU probes, PTO probes); never acknowledge an ACK-only packet on its own; never send Version Negotiation in reply to a v1 packet.
- Our CIDs are 8 bytes, byte 0 = worker index, bytes 1–7 from the CSPRNG; one server CID per connection while steering is on (spec §5.4).
- Every perf default the spec leaves "by measurement" is set from an A/B recorded in the ledger (`.superpowers/sdd/<plan>/progress.md`) with numbers.
- h1, h2 and WebSocket must not regress: shared-code changes are A/B'd; a regression > 1% on any of their profiles stops the task as BLOCKED with numbers.
- Downloaded repos, images and binaries (rival images, h3spec) are untrusted: build/run them only in Docker or in their own directory, never from inside our tree.

## Review Focus

1. **The client's first 1-RTT request coalesced after its Handshake Finished in one datagram** — must be served in the same turn (no wait for a retransmit). Test pinned in Task 7 (`coalesced_finished_and_request_served_in_one_turn`).
2. **A ClientHello that spans two Initial packets, or offers only key shares we do not support** (curl on OpenSSL 3.5 offers X25519MLKEM768) — reassembled across packets and both Initials reach the same worker; an unsupported-only offer fails fast with CONNECTION_CLOSE 0x128 (handshake_failure), never a hang. Tests in Task 6 (`client_hello_split_across_feeds`, `unsupported_key_share_only_is_handshake_failure`) and Task 10 (`second_initial_follows_forwarded_first`).
3. **`localhost` resolving to `::1` and IPv4 clients on the dual-stack socket** — replies leave from the exact address and port the client used (v4-mapped handled). Test in Task 11 (`dual_stack_replies_from_the_address_used`) and Task 15 (validation against `https://[::1]:8443` and `https://127.0.0.1:8443`).
4. **A POST body larger than the initial stream window from a client that never sends DATA_BLOCKED** — the server tops up MAX_STREAM_DATA/MAX_DATA unasked. Test in Task 8 (`large_upload_without_blocked_frames_completes`) and Task 14 (`post_body_over_window_reaches_handler`).
5. **A peer-initiated key update mid-connection** — the server must follow the key phase flip (RFC 9001 §6) and keep serving. Test in Task 5 (`key_phase_flip_decrypts_with_next_keys`) and Task 9 (`peer_key_update_mid_transfer`).
