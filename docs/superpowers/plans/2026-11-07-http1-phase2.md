# HTTP/1.1 phase 2 (async, json-comp, json-tls, 8gbit) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Complete the h1 family — add the four remaining scored profiles (async, json-comp, json-tls, 8gbit) on top of the merged h1 MVP, reusing its core/framework/driver, the h2 `JsonWriter`, and the existing user-space TLS.

**Architecture:** Two framework additions (h1-over-TLS; a timed-response path for async), then the four profiles as entry work on `arena-h1`. The sans-I/O core, parser, body decoder, response writer and io_uring driver are unchanged except for the TLS wiring and the timer await.

**Tech Stack:** Rust, `no_std`+`alloc` wtx; io_uring executor; existing user-space TLS (as h2/WebSocket); `rimu_ws::misc::JsonWriter`; in-tree `zlib-rs` (gzip); new `brotli` crate (json-comp).

**Spec:** `docs/superpowers/specs/2026-11-07-http1-phase2-design.md` (read with this plan; `/mnt/nvme1tb/claude-tmp/httpwin/rules.md` §2.3/§2.5/§2.6/§2.7/§3/§4 carry the exact request/response bytes and scoring).

## Global Constraints
- **Base:** local `main` @ `cf196b25` (h1 MVP + perf). Execution worktree cut from `main` via using-git-worktrees, under `/mnt/nvme1tb/claude-tmp`.
- **Tuned tier**; no pre-computed/cached/precompressed response bodies in any tier (validators draw random count/m and random bodies after startup); json-comp must compress per request.
- **Correctness is the gate.** Each profile passes its HttpArena validator and the MVP fragmentation gauntlet + full suite stay green; a perf number vs the rival images on colossus is reported, not required.
- **No model identifiers** anywhere except the commit `Co-Authored-By:` trailer (the session's attribution line). **Never push** rimu-ws or HttpArena.
- Never run two wtx test/bench processes at once; don't build during a benchmark. Temp/build under `/mnt/nvme1tb/claude-tmp`; use `CARGO_TARGET_DIR=/mnt/nvme1tb/claude-tmp/target-h1`.
- h1 test command: `--features http1-server-framework,web-socket,crypto-ring[,io-uring]` (the pre-existing cfg quirk; see MVP ledger).
- **Sequencing note:** phase-2 parallelizes poorly — the two framework additions share `http1_server_framework.rs`/`conn_driver.rs`, and the four profiles share `arena-h1.rs` + `meta.json`. Tasks run mostly sequentially; reviews may overlap.

## Review Focus
1. async: 32 concurrent requests, distinct delays 100–499 ms — each response ≥ 0.9× its own delay and never earlier than the delay; `/delay/0` immediate. → Task 3.
2. json-comp: `gzip`-only client → `gzip`; `br` offered → `br`; no `Accept-Encoding` → no `Content-Encoding`; decoded body matches the dataset for random count/m. → Task 4.
3. json-tls: ALPN selects only `http/1.1` (or nothing); weak TLS refused; JSON correct over TLS. → Task 5.
4. 8gbit: 1 B / 1 KiB / 10 KiB / 100 KiB and chunked bodies echoed byte-exact; empty body → 200. → Task 5.
5. The TLS listener and the timer path do not regress the plaintext MVP profiles (baseline/limited/latency still green + the fragmentation gauntlet). → Tasks 1, 2.

### Task 2: timed-response path for async (framework)

**Files:** Modify `wtx/src/http/http1_server_framework.rs` (Http1Res), `.../conn_driver.rs`. Test: framework `#[cfg(test)]`.

**Interfaces — Consumes:** Task 1 is independent of this (different feature, same files — sequential). **Produces:** `Http1Res::set_delay(core::time::Duration)` and `Http1Res::delay(&self) -> Option<Duration>`. After a handler returns, before writing the response, the driver's async connection future `await`s the executor's timer for `delay` (one io_uring timeout per in-flight delayed request); it never sends before the delay elapses. No handler blocks.

- [ ] **Step 1:** Write a failing loopback test `delayed_response_waits_not_early`: a route whose handler calls `res.set_delay(Duration::from_millis(60))` and sets body `"60"`; the client measures elapsed ≥ 55 ms and body `60`. Plus `concurrent_distinct_delays` (several connections, delays 40/80/120 ms, each ≥ 0.9× its delay).
- [ ] **Step 2:** Run → FAIL (`set_delay` absent).
- [ ] **Step 3:** Add `set_delay`/`delay` to `Http1Res`; in the driver, after the handler fills the response, if `delay()` is `Some(d)` await the executor timer for `d` before the send. Reset `delay` per response.
- [ ] **Step 4:** Run → PASS; whole suite green.
- [ ] **Step 5:** Commit `feat(http1): Http1Res::set_delay — driver awaits an io_uring timer before sending`.
